# Demo 14: Opossum Analysis — Blocker Report
**Date:** 2026-06-21
**Investigator:** GitHub Copilot
**Profile:** `ai4s` (data0.ai.r-ccs.riken.jp:50100)
**Status:** 2 critical blockers identified

---

## Summary

The demo was exercised end-to-end. Two critical blockers prevent successful
server-side workflow execution:

1. **Bucket alias not resolved** — `run-workflow --bucket demo-opossum` fails
   with `NoSuchBucket` because the workflow runner uses the alias directly as
   the S3 bucket name instead of resolving it to
   `mnagaso2.opossum-analysis.demo-opossum`.

2. **Step receives no input keys** — The workflow runner only populates
   `ctx.input_keys` from upstream step outputs. For entry-point steps with no
   dependencies (like `opossum_analyze`), `ctx.input_keys` is empty, so the
   step has no videos to process and produces 0 events.

---

## Blocker 1: Bucket Alias Not Resolved (CRITICAL)

### Symptom
```
umrs-client run-workflow opossum-analysis --bucket demo-opossum
→ job fails: "NoSuchBucket when calling the PutObject operation"
```

### Root Cause
`umrs/src/umrs/server/workflow_runner.py` line ~593:
```python
bucket = record.params.get("bucket", "wf-runner")
```
The `bucket` parameter is used directly as the S3 bucket name. When the user
passes `--bucket demo-opossum` (the alias), the workflow runner tries to write
to bucket `demo-opossum-output`, which doesn't exist in MinIO.

The actual MinIO bucket names follow the convention:
- Input: `<username>.<experience_name>.<bucket_alias>`
- Output: `<username>.<experience_name>.<bucket_alias>-output`

For this demo:
- Input: `mnagaso2.opossum-analysis.demo-opossum`
- Output: `mnagaso2.opossum-analysis.demo-opossum-output`

### Workaround
Pass the full bucket name instead of the alias:
```bash
umrs-client run-workflow opossum-analysis \
  --bucket mnagaso2.opossum-analysis.demo-opossum
```

### Proper Fix
The workflow runner should resolve the bucket alias to the full MinIO bucket
name, similar to how `upload_dir` does it via `check_bucket_name()`.

## Blocker 2: Step Receives No Input Keys (CRITICAL)

### Symptom
Workflow completes successfully (status: `completed`), but produces empty
output:
```json
{
  "gpu_accelerated": false,
  "cameras_analyzed": [],
  "total_pairs": 0,
  "total_events": 0
}
```

### Root Cause
`umrs/src/umrs/server/workflow_runner.py` line ~437:
```python
upstream_keys: list[str] = []
for dep in spec.get("depends_on") or []:
    dep_result = parent_results_snapshot.get(dep)
    if dep_result is not None:
        upstream_keys.extend(dep_result.output_keys)

ctx = StepContext(
    s3=s3_client,
    input_bucket=bucket,
    input_keys=upstream_keys,  # ← empty for entry-point steps
    output_bucket=bucket + "-output",
    ...
)
```

The `input_keys` field is only populated from upstream steps' outputs. For
entry-point steps with no `depends_on` (like `opossum_analyze`), `input_keys`
is empty.

The `OpossumAnalyzeStep.run()` method calls:
```python
cameras = self._group_by_camera(ctx.input_keys)  # ← empty list
```
With an empty `input_keys`, `cameras` is an empty dict, and the step produces
no output.

### Fix Options

**Option A: Step lists bucket contents (recommended)**
The step should use `ctx.s3.list_objects(Bucket=ctx.input_bucket)` to discover
input videos when `ctx.input_keys` is empty.

**Option B: Workflow runner populates input_keys from bucket**
The workflow runner could list the input bucket and populate `input_keys` for
entry-point steps. This is more complex and changes the runner's contract.

**Option C: Pass input keys via workflow params**
The user could pass `--params '{"input_keys": ["key1", "key2"]}'` to
`run-workflow`. This is manual and doesn't scale.

### Recommended Fix (Option A)
Add a `_discover_input_keys()` method to `OpossumAnalyzeStep` that lists the
input bucket when `ctx.input_keys` is empty:

```python
def _discover_input_keys(self, ctx: StepContext) -> list[str]:
    """List input bucket for video keys when input_keys is empty."""
    resp = ctx.s3.list_objects_v2(Bucket=ctx.input_bucket)
    return [obj["Key"] for obj in resp.get("Contents", [])
            if obj["Key"].endswith(".mp4")]
```

Then in `run()`:
```python
input_keys = ctx.input_keys or self._discover_input_keys(ctx)
cameras = self._group_by_camera(input_keys)
```

## Blocker 3: GPU Not Used (MINOR)

### Symptom
`analysis_summary.json` shows `"gpu_accelerated": false`.

### Root Cause
The workflow runs in-process (`InProcessExecutor`) on the server, which
doesn't have CUDA-enabled OpenCV. The `routing_hints.image` and
`routing_hints.gpu` in `workflow.json` are only used by the `PodmanExecutor`,
which is not the default executor.

### Fix
Set `UMRS_STEP_EXECUTOR=podman` and `UMRS_STEP_IMAGE=<cuda-image>` in the
server environment, or configure the workflow to use the Podman executor.

## Conclusion

The demo's server-side workflow execution is blocked by two critical issues:

1. **Bucket alias resolution** — The workflow runner doesn't resolve bucket
   aliases to full MinIO bucket names. Workaround: pass the full bucket name.

2. **Empty input keys** — The workflow runner doesn't populate `ctx.input_keys`
   for entry-point steps. The step has no videos to process and produces empty
   output. Fix: the step should list the input bucket contents when
   `ctx.input_keys` is empty.

Both blockers are in `umrs/src/umrs/server/workflow_runner.py`. The demo's
local analysis path (running `opossum_step.py` directly with cv2) works fine,
as documented in `REPORT_2026-06-17.md`.
