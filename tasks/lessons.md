# Lessons

- 2026-03-27: Demo 01 `run_demo.sh` status parser crashed on non-dict items in summaries JSON. The `check` and `update` categories contain string items (bucket names), but the parser assumed all `data` entries are dicts with `.get("status")`. Fix: filter with `isinstance(t, dict)` before calling `.get()`. Always guard against mixed-type lists in API responses.
- 2026-03-27: `embedding_backend=remote` + `embedding_worker.py` (ZMQ REQ/REP standalone worker) was superseded by mini-rivault (vLLM + LiteLLM on Slurm compute nodes, accessed via OpenAI-compatible `/v1/embeddings` API through SSH tunnel). When a new compute approach replaces an old one, audit **all** layers: Python code (`embedding_backend.py`, `embeddings.py`, `s3.py`), configs (`conf_umrs.json`, JSON schema in `json_utils.py`), Docker compose files, K8s manifests, deploy scripts, kustomization references, and documentation. The presigned URL path in `compute_embeddings_core()` and `load_data_from_presigned_urls()` in `s3.py` were also dead code since only the removed worker consumed them (vision service has its own presigned URL path in `s3_presign.py`). Total removal: 14 files, -1106 lines.
- 2026-03-06: Make DB/user provisioning idempotent under concurrent startup/reload. Avoid check-then-create races by handling `DuplicateDatabase`/`UniqueViolation` as success for `CREATE DATABASE`, and always run `CREATE EXTENSION IF NOT EXISTS vector` after connecting to target DB.
- 2026-03-06: Task stacking — `UMRSTask.add_task()` had no deduplication; each client request or recovery attempt created a new row for identical (client_id, cmd, payload). Fix: check for existing active (Submitted/Running) task before INSERT. Also, `launch_rivault_model()` had a race condition where concurrent threads each submitted a new Slurm job before the first one cached the job_id. Fix: serialize with `threading.Lock`. Also, `process_s3_objects()` should `continue` to next bucket when rivault model launch fails, not just set exit_status.
- 2026-03-06: `configure_table()` in sql.py crashes with `UniqueViolation` on `pg_class_relname_nsp_index` when a SERIAL column's sequence already exists (leftover from partial table creation or race). Fix: wrap `CREATE TABLE` in try/except for `UniqueViolation`/`DuplicateTable`, rollback, and treat as "table already exists". Same pattern as `create_db()` — all DDL in UMRS must be idempotent.
- 2026-03-08: LiteLLM requires API key (Bearer token) for ALL endpoints including `/v1/models`. `wait_for_model()` was doing unauthenticated GET requests → always got 401 → timed out after 60s. Fix: thread `LITELLM_MASTER_KEY` from env through `wait_for_model()`, `get_client()`, `get_max_tokens_from_vllm()`, and `is_server_alive()`. Also increase timeout from 60s to 300s since vLLM initialization can be slow. Also: `podman-compose ps -q <service>` is not supported — use `podman ps -q --filter name=...` instead.
- 2026-03-08: E2E demo scripts must never infer "success" from the absence of "running" tasks — Error/Failed states also show 0 running. Fix: phase3 now explicitly detects Error status and fails. Also: always verify DB state (rows + non-null embeddings) as a final gate, not just the UMRS task status. Added `phase3b_verify_embeddings_in_db()` to query pgvector databases directly.
- 2026-03-08: `sudo killall munged` on the host kills ALL munged processes including those running inside rootless podman containers (the container's PID namespace is visible from host). This causes munge containers to exit and downstream services (slurmctld) to lose auth. Fix: use targeted `kill <pid>` for the specific host munged, or use `systemctl stop munge` if running via systemd.
- 2026-03-08: LiteLLM Prisma tables (`LiteLLM_Config`, `LiteLLM_CredentialsTable`, `LiteLLM_ProxyModelTable`) may not exist if LiteLLM's internal postgres wasn't properly migrated. This prevents the LiteLLM proxy from functioning, breaking the nginx→LiteLLM→vLLM chain. HTTP requests to the nginx front-end will time out even though vLLM itself is healthy.
- 2026-03-15: Stale `import torch` in `umrs/utils.py` prevented the `umrs-client` CLI from working in a client-only venv (torch not needed for client deps). Always check import chains when making a package pip-installable — unused imports of heavy deps will block lightweight installs.
- 2026-03-15: Bash brace expansion (`*.{jpg,png,tiff}`) fails silently with `set -u` / strict mode, causing "unexpected token" errors. Use `find -name '*.jpg' -o -name '*.png'` instead for portable file matching in scripts.
- 2026-03-15: BentoML vision models should run ONLY inside Mini-Rivault sandbox for security (per-job isolation, offline mode, no DNS, read-only weights, tmpfs scratch). Never deploy as a shared long-lived service — cross-user data leakage risk. Route through NGINX `/vision/` prefix so single SSH tunnel covers all services.
- 2026-03-17: `pretty_print_tasks()` in UMRSTask.py fetched ALL historical tasks (~5600+) and printed them as a tabulate table on every event loop iteration and every status update. This blocked the server event loop for 10-30+ seconds, causing ZMQ client timeouts (8s) to expire when `upload_dir` ran after `reload`. Fix: add `limit=N` parameter to only show the N most recent tasks. The blocking was the root cause of vision PROCESS_OBJECTS messages being lost after RELOAD.
- 2026-03-17: `BentoMLTaskClient(base_url)` was being passed the full endpoint URL (e.g. `http://host:port/vision/sam3_segment/submit`) instead of the service base URL (`http://host:port/vision`). This caused `is_healthy()` to check `…/sam3_segment/submit/healthz` (404) instead of `…/healthz` (200), making the health check loop for 300s before timing out. Also caused doubled paths in `submit()` calls. Fix: derive `service_base_url` by stripping the endpoint name from the URL path.
- 2026-03-24: `client_umrs.py` `model download --server-side` had an indentation bug: the `MODEL_REGISTER` call and its dict-closing `})` were at 20 spaces (same as the if/else), so they ran unconditionally after both branches. When `--server-side` was True, MODEL_DOWNLOAD fired (correct) then MODEL_REGISTER fired with the server-side payload (no `path` field) → "Model path is required". Fix: re-indent `})` and `raw = ...MODEL_REGISTER...` from 20 to 24 spaces (inside the `else:` block).
- 2026-03-24: The deployed BentoML vision container still runs the old `service.py` (Jens's `VisionFrontend` with `/vision_task/submit` endpoint), but the client-side `bentoml_adapter.py` was refactored to call `/infer/submit`. This endpoint mismatch causes 404 errors. Additionally, the 404 error handler in BentoML `SyncHTTPClient` crashes with `AttributeError: 'SyncHTTPClient' object has no attribute '_opened_files'` — a latent bug in the bentoml library's error cleanup path. Fix: rebuild the vision Docker image with the updated `service.py` and save a new tarball.
- 2026-03-24: BentoML 1.4.36 `ResultStatus` enum uses `COMPLETED="completed"`, `FAILED="failed"`, `CANCELED="canceled"` — NOT `"success"`, `"failure"`, `"cancelled"`. The status poll loop in `bentoml_adapter.py` checked wrong string values for ALL three terminal states, causing infinite polling until timeout. Always verify enum values against the actual library source, not docs or assumptions.
- 2026-03-24: Adapter auto-discovery uses `py_file.stem` as the registry key. If adapter files are named `sam3_adapter.py`, the key becomes `"sam3_adapter"` but the server sends `model_type="sam3"`. Fix: `py_file.stem.removesuffix("_adapter")` to strip the conventional suffix. Convention: adapter files should be named `<model>_adapter.py`.
- 2026-03-24: `DEFAULT_ADAPTERS_DIR` in the Slurm wrapper defaulted to `${RIVAULT_DIR}/default_adapters` but the actual adapter files live at `src/umrs/vision_service/default_adapters/` (baked into the Docker image). The `mini-rivault-llm/default_adapters/` directory was empty (root-owned). Fix: change path to `${RIVAULT_DIR}/../vision_service/default_adapters`.
- 2026-03-24: Rogue Python scripts in directories mounted as adapter paths (e.g. `/tmp`) can crash the BentoML container if they call `sys.exit()`. The adapter loader uses `importlib exec_module()` which propagates `SystemExit`. Fix: catch `SystemExit` alongside `Exception` in the adapter loading try/except.
- 2026-03-24: When containers have dependencies (e.g. pods), `podman rm` fails with "has dependent containers". Regular compose-down may not clean them up. For aggressive cleanup: `podman stop -a -t 0 && podman rm -af && podman network prune -f`. Deploy this as a Slurm job when iterating on container configurations.
- 2026-03-25: Podman storage.conf with `graphroot` on tmpfs + `force_mask="700"` causes cascading build failures: (1) xattr "operation not permitted" on `COPY --from`, (2) `su: Permission denied` in package postinst scripts (setuid stripped), (3) intermittent `mknod ENODATA` from stale overlay state. Fix: use local ext4 graphroot, remove `force_mask`. The NFS comment in storage.conf was outdated — verify filesystem assumptions before trusting config comments.
- 2026-03-25: Demo directory numbering inconsistency: workflow.json paths in demos 08 and 09 referenced old directory numbers (06, 07) that no longer existed, causing step loading failures. When renumbering demo directories, always search for hardcoded paths across all JSON/YAML/MD files.
- 2026-03-25: Building munge package in rootless Podman: even on ext4, the munge postinst script may fail with `su`. Use defensive pattern: `apt-get install ... munge || true && dpkg --configure -a --force-all || true` to tolerate postinst failures.
