What the GB10 pair shows

  • 2.3×Single-stream decode drops from 45.3 to 19.5 tok/s when the two tensor-parallel ranks talk over 10 Gb/s TCP instead of 200 Gb/s RoCE. Same nodes, engine, weights and settings.
  • +28 msThe added time per token. Decode is latency-bound on the link: an 8 KiB all-reduce takes 23 µs over RoCE and 445 µs over TCP, and the ranks exchange small messages many times per token.
  • 2.5×Prefill falls from ~2,050 to ~805 tok/s over TCP and stays flat from 12k to 87k tokens: it hits the link's bandwidth ceiling (1.17 GB/s). Over RoCE it matches the recipe author's figure (~2,150 tok/s), so there it is compute-bound, not link-bound.
  • 1.3–1.9×Decode gain from the checkpoint's DSpark draft blocks (58 / 84 tok/s for prose / code). They fit in memory on rccs after all: 9 GiB left per node after load.
  • ~13 msThe memory-bandwidth floor per decoded token on GB10 (≈2.9 GB of active weights per rank at 227 GB/s measured). The measured 21.4 ms leaves about 8 ms for synchronisation, launches and sampling.

Two platforms

Both serve the same model, DeepSeek-V4.1-Flash-1017 (552B total MoE backbone parameters, about 16B active per decoded token, plus Engram lookup tables). They cannot share one engine. The MiaAI recipe's kernel kit is 203 cubins built for the GB10 (sm_121), which do not load on the RTX PRO 6000 (sm_120), and one of its TP=2 ranks needs ~99 GiB, more than a 96 GB card. So the PRO 6000 side serves NVIDIA's NVFP4 checkpoint with SGLang. Engine and quantization differ along with the hardware, and the comparison table marks it.

Reading the numbers

Decode is bandwidth plus latency

A decoded token reads the active weights once. At ~16B active parameters and 2.9 bits a weight, each rank reads about 2.9 GB per token; at the 227 GB/s the GB10 copies at, that is ~13 ms, a ceiling near 78 tok/s per stream without drafts. The measured 21.4 ms per token over RoCE leaves ~8 ms for the ranks' synchronisation, kernel launches and sampling.

Over TCP each token costs 28.2 ms more. The small-message all-reduce penalty is 445 − 23 = 422 µs, so the extra time equals about 67 latency-bound exchanges per token. Bandwidth barely matters here: a decode exchange is kilobytes. What matters is the link's round-trip, which is why the 10G NIC loses so much on decode even though decode moves little data.

Prefill shows the link's bandwidth

Over TCP, prefill flattens at ~805 tok/s from 12k tokens up, which at the measured 1.17 GB/s means about 1.45 MB crosses the link per prompt token. At RoCE's prefill rate that is ~3 GB/s, a quarter of what the rail delivers (12 GB/s), so on RoCE prefill is limited by compute and Engram reads, matching the recipe author's 2,105–2,154 tok/s on Sparks with local Engram.

Concurrency and drafts

Four streams lift aggregate decode to 104 tok/s without drafts and 151 with them (code). Per-stream speed falls as streams share each round. The drafter helps code most (84 vs 44 tok/s), where draft blocks are accepted often; prose gains less (58 vs 46). Long prompts queue: with four concurrent 6.1k-token prompts, time to first token reaches 16–22 s because prefills of other streams run ahead.

Distance to the recipe's own figures

The recipe reports 80.7 tok/s (prose) and 118.1 (code) for one stream with drafts on; rccs measures 58 and 84. Prefill matches. Differences on rccs: one addressed QSFP rail instead of two, a 131,072-token pool instead of 524,288, and the GB10s at their default 2,418 MHz application clock instead of a 2,200 MHz lock (the opposite direction). The single rail is the likely cause; assigning an IPv4 to the twin port is a host change for RCCS.

RTX PRO 6000 leg

Queued: rccs job 468124 holds both ai-pro6000 nodes for 23 h once they free up (other users' jobs run there now; Slurm's estimate was 2026-11-14 22:10). When it starts it probes the nodes, launches SGLang at TP=4, runs the same serving benchmark at 1–8 streams, then the all-reduce and memory benchmarks intra-node (PCIe) and inter-node (RDMA if present, and TCP), and keeps serving. This page is updated with those results.

What the comparison isolates when it lands:

  • Memory bandwidth. GDDR7 on a PRO 6000 is several times the GB10's 227 GB/s, and TP=4 splits the active weights four ways, so the per-token bandwidth floor drops by an order of magnitude. Decode should no longer be bandwidth-bound; synchronisation takes over.
  • Topology. TP=4 mixes a PCIe hop inside a node with a network hop between nodes in every all-reduce, so the slower hop sets the pace, as the single TCP link did on the GB10 pair.
  • Unified versus discrete memory. The GB10 shares one pool between host and GPU: weights, Engram and the OS compete, which is what forced the drafter and reserve decisions. The PRO 6000 nodes keep Engram in 1 TB of host RAM and read it across PCIe.
  • Engine and quantization. TensorFold EXL3 2.9 bpw versus SGLang NVFP4 4 bit. This difference is confounded with the hardware and the report says so beside each number.

Method and caveats

  • Client: serve_bench.py (standard library only), streaming OpenAI chat API, run on each platform's head node. Decode tok/s counts output tokens after the first over the time to the last chunk; prefill tok/s is prompt tokens over time to first token.
  • Hardware numbers: hw_bench.py (PyTorch 2.13, NCCL 2.30.7) in the serving image; raw RDMA with ib_write_bw / ib_write_lat.
  • Two repetitions per point, medians shown. Single-stream decode varied by ±3 tok/s between repetitions.
  • The GB10 nodes run in rccs's shared Lustre environment: ~15 GiB of kernel slab stays resident, so a job gets ~105 GiB of the 121.6 GiB. The recipe asks for 112 GiB free; it runs here with vision off, a 131,072 context, a 100 GiB pre-start reclaim and the engine reserve at 11.5 GiB.
  • Scripts, staging and the serving entries: umrs branch feat/dsv41-rccs-pro6000, deploy/rccs/dsv41/. Raw JSON: ~/tmp/dsv41/bench/ on rccs.
